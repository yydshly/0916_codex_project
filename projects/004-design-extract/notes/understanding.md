# Design Extract：能力、Codex 对比与我们的参考价值

整理日期：2026-09-16。基于本次讨论、源码阅读和保留的实验记录。研究版本为 designlang 13.3.0 / 47f75bb68cd6fcb51c172868a3a1b814cd6bdeb4。

## 先给结论

**库的能力：** 从网页提取配色、字体、间距、布局与部分交互状态，通过规则归纳为设计资料，导出设计文档、样式变量和主题配置。

**对我们的意义：** 为批量分析参考站、复用设计规范和构建网页复刻工具提供现成的采集模块与工程参考。值得借鉴的是浏览器采集、数据组织和导出接口；完整复刻还需要代码生成、运行预览、同状态对比与修改验证。

对于一次只复刻一个网页的需求，可以直接让具备浏览器工具的 Codex 观察、测量、实现和调整。引入这个库未必提高准确度或节省时间；我们尚未做两种流程的对照实验。

如果要建立可重复、可批量执行的网页复刻能力，这个库可承担部分采集工作；还需要补上页面生成、运行预览、同状态对比和修改验证。

## 1. 它的能力和原理

主流程：网页 URL → Playwright 打开页面 → DOM / 计算样式 / CSS 规则 → 统计与分类 → 统一设计对象 → 文档、变量、主题配置和模板。

| 能力 | 输出 | 本轮边界 |
| --- | --- | --- |
| 基础样式采集 | 配色、字体、字号、间距、圆角、阴影等 | 已核验一个原创样本的具体读数 |
| 状态采集 | 明暗模式、不同视口、悬停和聚焦的变化 | 已做局部实验；不等于可探索任意点击流程 |
| 设计资料导出 | DESIGN.md、CSS、设计变量 JSON、各类主题配置 | 30 个导出器返回内容，未逐一验证导入与编译 |
| 页面起点生成 | 组件骨架和 Next.js 模板文件 | 生成文件已检查，未构建验证完整复刻 |
| 检查、差异及 MCP | 对比度结果、差异相关命令、Agent 调用接口 | 各项验证程度不同；未证明完整自动复刻可用 |

截图是视觉参考；该库的基础设计提取主要读取浏览器结构和样式，不是单凭截图用大模型猜测参数。--smart 是可选分类辅助。

必须区分三类信息：

- **观测**：浏览器读到按钮背景为 #2563eb，只代表当时的页面状态。
- **推断**：判断这个颜色代表品牌主色，可能误判。
- **生成**：推导新色阶、填入模板文案，并不意味着原站出现过。

本次样本的 17 项基础检查通过，同时有 4 项独立保真检查未通过：间距归纳漏值、正文色误选、慢动画捕获中间态、页面模板加入原站没有的文案。这不是复杂网站准确率统计。详见 [实验结果](verification.json) 与 [源码分析](architecture.md)。

## 2. 直接交给 Codex，差别在哪里？

下面描述的是具备相应工具时可观察的工作流程，不是对未公开模型内部机制的断言，也不是每次任务都会自动执行的固定步骤。

Codex 可采用：观察网页 → 判断缺失信息 → 调用浏览器补充测量 → 编写页面 → 运行预览 → 对照修改。

Design Extract 主要采用：按已实现的采集项读取网页 → 按规则归纳 → 按统一格式导出。

| 比较项 | 直接用 Codex | 使用 Design Extract |
| --- | --- | --- |
| 工作组织 | 根据任务动态选择检查内容和实现方式 | 预先编写的采集、分类和导出流程 |
| 获取信息 | 依赖实际可用工具；可看截图，也可读取结构和样式 | 封装浏览器采集和设计数据整理 |
| 精确读数 | 实际测量可以得到精确值；视觉估计可能错误 | 原始值可以准确；后续归纳仍可能丢失或误选 |
| 主要产物 | 当前需求下的代码与页面 | 可复用的设计资料；另有模板输出 |
| 复用方式 | 明确保存文档、脚本、组件或 Skill | 现成 CLI / API / MCP 与统一输出格式 |
| 质量保障 | 需要实际运行、比较和修改 | 也需要校验；引入工具不自动提高保真度 |

例子：原站卡片 gap 为 24px。只看截图可能估错；浏览器测量可以读到 24px。我们实测中，该库读到了这个值，但归纳后的间距尺度没有保留它。因此应同时保留原始读数与归纳结果。

两者可以组合：Codex 调用该库拿到设计数据，再结合截图和关键测量生成页面。它们并非互斥方案。

## 3. 两种“对比”不要混淆

| 对比 | 回答的问题 | 能力范围 |
| --- | --- | --- |
| 原网页操作前后对比 | 原站在悬停、聚焦或尺寸变化后怎样变化？ | 库已有部分能力；任意菜单、弹窗和业务流程仍需补充探索 |
| 原网页与复刻网页对比 | 两边在相同视口和状态下是否一致？ | 完整流程还需实现状态对应、视觉检查、定位与修正 |

以展开菜单为例：记录原站关闭与展开状态 → 生成菜单 → 在复刻页执行同样操作 → 比较展开后的内容、位置和样式 → 修改 → 再检查。

即便库提供差异或评分命令，也不能据此认定它已完成“生成代码—运行—定位问题—修改—复验”的整个过程。此过程本轮未端到端验证。

## 4. 我们在什么情况下使用？

| 场景 | 建议 | 预期价值与限制 |
| --- | --- | --- |
| 偶尔复刻一个喜欢的网页 | 先直接用 Codex，要求关键测量和截图检查 | 增加提取工具未必有收益 |
| 多个项目沿用同一套风格 | 可用该库提取，再人工确认并保存规范 | 复用颜色、字体和组件参数，不会自动移植业务 |
| 批量整理参考站 | 值得试用统一采集接口 | 需要记录来源、处理失败并抽查准确性 |
| 旧站改版与样式盘点 | 可作为设计资料整理工具 | 现状中的不一致不应全部变成新规范 |
| 制作自动复刻工具 | 借鉴或接入采集与导出模块 | 仍需生成、运行、对比和修正流程 |
| 已有完善组件库和设计变量 | 优先使用项目已有规范 | 无需重复从外部页面提取同类资料 |

只提供截图时，该库的 URL 采集流程不能直接使用；应走截图理解路线。后端接口、权限和真实业务行为需要另行开发。

## 5. 对我们实现复刻能力的参考价值

### 可以借鉴

1. **浏览器采集**：实际读取运行后的样式，覆盖多视口、主题和部分交互状态。
2. **数据组织**：把零散页面信息整理成可供代码生成使用的结构化资料。
3. **导出接口**：同一份信息导出成文档、变量和不同技术栈配置。
4. **集成方式**：CLI、API 和 MCP 方便接入更大的工作流程；接入本身不提高准确率。

### 需要补强

1. **数据溯源**：每个值关联元素、视口、状态和截图；保留原始值，分开记录推断。
2. **交互探索**：识别菜单、折叠面板和标签页，记录操作前后的状态；限制探索范围。
3. **代码生成与运行**：按区域和组件实现，实际构建并打开预览。
4. **同条件比较**：统一浏览器、字体、视口、内容和状态，分别检查视觉与行为。
5. **差异驱动修改**：指出哪里不同、可能原因、应修改的组件；修改后重新验证，设置轮次上限。

建议流程：参考网页 → 截图与结构样式采集 → 有来源的页面资料 → 生成前端代码 → 启动预览 → 同视口同状态比较。仍有差异则回到代码修改，达到要求再交付源码与验证报告。

## 6. 技术探索与下一步实验

以下是建议方案，不是已实现或已验证的产品能力。

| 层次 | 可探索技术 | 目的 |
| --- | --- | --- |
| 浏览器采集 | Playwright + Chromium | 截图、读取结构与计算样式、操作和多视口采样 |
| 设计信息整理 | 自定义数据格式；Design Extract 作为候选模块 | 同时保留事实、推断和来源 |
| 页面生成 | 支持视觉输入与编码的模型；第一版固定前端框架 | 按区域重建为可维护组件 |
| 视觉验证 | Playwright 截图比较 / pixelmatch；模型辅助解释 | 定位差异；不能只靠单一评分验收 |
| 交互探索 | 固定操作脚本；后续研究 Stagehand | 从有限、明确的交互开始 |

第一版范围建议为单个公开页面、桌面与手机布局、少量常见交互，交付源码、预览和差异报告。先完成采集—生成—比较—修正，再扩展多页与批量处理。

下一步最值得做的是同页三组实验：A 仅截图；B 截图 + 自行采集的结构样式；C 截图 + Design Extract 输出。固定模型、提示要求、目标框架、素材条件和最大修正轮次；记录视觉差异、交互检查、人工修改量、耗时与成本。样本应覆盖展示页、卡片列表、响应式布局和含菜单的页面。条件允许时重复运行，避免以单次生成判断优劣。

目前没有证据证明 C 一定优于 B 或 A；应让实验决定是否集成这个库。
