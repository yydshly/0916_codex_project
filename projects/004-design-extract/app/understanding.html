004 / RESEARCH NOTES · 我们的理解

从采集网页，
到真正完成复刻。

从网页提取配色、字体、间距、布局与部分交互状态，导出设计文档和主题配置。对我们，它为批量分析参考站、复用设计规范和构建网页复刻工具提供采集模块与工程参考；完整复刻仍需生成、运行、对比与修正。

01 / CAPABILITY

它封装了哪些能力？

基础提取主要读取结构和样式。截图提供视觉参考，可选模型辅助部分分类。

01 · 获取信息

读取浏览器里的页面

采集颜色、字体、间距、布局；观察不同视口、明暗模式、悬停与聚焦的变化。

02 · 整理信息

把读数归纳为设计资料

统计、聚类并推断主色和间距尺度。必须区分实际观测、含义推断与新生成的数据。

03 · 导出复用

交给人、工具和 Agent

输出设计文档、变量和主题配置；另有模板与差异相关功能。导出文件不代表完整还原网站。

打开网页→读取结构与样式→按规则归纳→导出设计资料
证据边界：一个原创样本，17 项基础检查通过；另有 4 项保真检查未通过：间距漏值、正文色误选、慢动画中间态、模板文案。查看原始研究 →
02 / COMPARE

直接交给 Codex，有什么差别？

获取数据可以使用相同方法。差别在工作组织、输出形式，以及是否继续运行和修改。

比较项直接用 CodexDesign Extract
怎么做根据任务选择观察、测量和实现步骤按预先实现的采集、分类与导出流程执行
获取信息有对应工具时，可查看截图、结构和样式封装浏览器采集，生成统一设计对象
主要产物当前任务的代码和页面设计资料与主题配置；另有页面模板
复用方式保存文档、组件、脚本或 Skill通过 CLI / API / MCP 重复调用
准确性实际测量可精确；估计和推断可能出错原始读数可精确；整理过程也会误判

这里描述具备相应工具时的可观察工作流程，不是对未公开模型内部机制的断言，也不保证每次任务自动执行全部步骤。OpenAI 工作流参考 ↗

一个 24px 间距，就能说明问题。

只看截图可能估错；实际读取样式可以得到 24px。我们实测中，库读到了这个值，却在归纳尺度时遗漏了它。

决定准确度的是测量、信息保留和复验。引入库本身不保证更准确。

03 / TWO COMPARISONS

两种“对比”，回答不同的问题。

“点击后再获取信息”属于状态探索；“生成后对照原站”属于复刻验证。

库已有部分能力

原网页：操作前 → 操作后

理解悬停、聚焦、主题和尺寸变化。菜单展开、弹窗和任意业务流程，还需要补充探索与验证。

完整流程需要补齐

原网页 ↔ 复刻网页

在相同视口与状态下比较外观和行为，定位差异、修改代码，再检查。已有差异命令不等于完成全部流程。

记录原站展开菜单→生成菜单→操作复刻菜单→对比展开状态→修改并复验
04 / WHEN TO USE

按需求决定是否引入。

单次开发先直接做；当采集和整理反复出现时，再评估工具的收益。

先直接用 Codex。

要求观察参考页、读取关键参数、实现后对照截图。加一道提取步骤未必更省事；我们没有验证这个库能提升单次复刻效果。

只有截图时，URL 采集流程不能直接使用。已有完整设计规范时，优先沿用现有组件和变量。后台接口、权限和真实业务需要另行实现。

05 / VALUE FOR US

借鉴采集与导出，补齐验证与修正。

建议先做单页、桌面与手机布局、少量常见交互，交付源码、预览和差异报告。

建议架构 · 尚未实现验证
浏览器采集→有来源的资料→生成代码→运行预览→同条件比较

发现差异 → 定位原因 → 修改代码 → 再次验证

Design Extract 可作为前段采集与整理模块。完整系统还要能解释哪里不同、改哪里，以及修改后是否改善。

值得借鉴的部分

  • Playwright 读取运行后的页面与样式。
  • 多视口、主题和部分交互状态采样。
  • 统一设计对象与多种导出格式。
  • 通过 CLI / API / MCP 接入工作流程。

我们需要补强的部分

  • 保留原始值及元素、视口、状态来源。
  • 明确交互探索范围，建立状态对应。
  • 生成可维护组件并实际构建、运行。
  • 视觉与行为分开验证，按差异修改并设轮次上限。
技术方向候选方案用途
采集Playwright + Chromium结构、样式、截图和状态采样
整理自定义资料格式 + 可选 Design Extract保留观测、推断与来源
生成视觉与编码模型；第一版固定前端框架按区域和组件实现
比较Playwright / pixelmatch + 模型辅助解释定位视觉差异；另外验证交互
探索固定操作脚本；后续研究 Stagehand逐步扩大交互覆盖
