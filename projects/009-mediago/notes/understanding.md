# 我们的理解：MediaGo 如何把输入变为媒体文件

**获取输入 → 识别资源类型 → 选择对应引擎 → 解析并下载 → 合并、检查与保存。**

**MediaGo 主要负责识别、分派和管理；具体解析与下载主要交给对应引擎。**

这是对架构的概括，不是所有输入都必须经过完全相同的步骤。MediaGo 也实现 HLS 清单信息检查；合并只在需要时进行，下载成功后的格式转换是可选步骤。

## 输入不一定已经是真正的视频源

- **普通网页**：先打开网页并触发播放，通过浏览器请求发现媒体地址，再选择和下载。
- **已适配的网站视频页**：可以先选 BBDown 或 yt-dlp，由引擎理解网站页面和接口，再找出可下载媒体。
- **m3u8 地址**：已经得到播放清单，检查变体后可让引擎下载相应数据。
- **MP4 等文件直链**：已经知道目标文件位置，直接下载即可。

因此“先获取视频源，再判断下载方式”有时成立；更通用的说法是“先获取输入，再选择解析与下载路径”。网页、清单和文件本身是不同层次。

## 三个容易混淆的词

| 概念 | 它在做什么 | 结果 |
| --- | --- | --- |
| 浏览器嗅探 | 观察页面实际发出的网络请求，通过 URL 和部分响应类型识别媒体 | 候选地址、类型、标题与请求上下文 |
| 引擎解析 | 根据特定站点的规则和接口取得媒体信息 | 真实媒体 URL、格式、画质和音视频轨等 |
| 清单 | 描述可选版本或媒体分片的文本目录；此处主要指 HLS m3u8 | 主列表列画质与变体，媒体列表列分片和顺序 |

下载一份 m3u8 文本不等于保存了完整视频。引擎还要获取其中对应的数据；直播的媒体清单会持续更新。嗅探和引擎解析是找到资源的不同途径，也可能在同一任务中配合使用。

## 支持哪些资源及下载方式

| 资源与输入 | MediaGo 类型 | 执行引擎 | 如何下载 |
| --- | --- | --- | --- |
| HTTP 媒体文件直链，如 MP4、FLV、MOV、AVI、MKV、WMV、M4A、OGG 等 | direct | aria2c，分发源为 aria2-next | 文件传输；通常不需要站点解析或分片合并 |
| HLS / m3u8 点播、可访问的 HLS 直播流 | m3u8 | N_m3u8DL-RE | 读取清单，获取片段和音视频数据，必要时合并；直播持续接收并收尾 |
| Bilibili 对应视频页，Core 类型推断也包含 b23.tv | bilibili | BBDown | 站点解析，下载可用音视频流并按需要合并 |
| YouTube、X/Twitter、抖音/TikTok 等已适配页面 | youtube | yt-dlp | 对应站点解析器取得媒体信息，再传输并按需要合并 |
| 小红书视频笔记及分享链接 | xiaohongshu | yt-dlp | 独立类型保留笔记签名等上下文，由 yt-dlp 解析下载 |
| 显式选择的另一下载通道 | mediago | 外部 mediago 二进制 | 源码确认入口存在；本次未审计该独立引擎完整协议及站点范围 |

六种类型对应五个下载执行入口。FFmpeg 作为辅助工具承担音视频合并和格式转换；Deno 为 yt-dlp 提供 JavaScript 运行环境。

Instagram、Reddit 及更多网站来自 yt-dlp 的解析范围，不代表 MediaGo 为每个站点提供了自动识别规则。未知页面可能默认走 direct，需要明确选择对应类型。页面路径、账号权限、请求头、签名有效期和网络条件仍会影响结果。

## MediaGo 自己解决的问题

它把“找资源”和“执行下载”组织成可追踪流程：统一入口与类型识别、必要上下文传递、下载器参数适配、数据库记录、并发队列、启动停止、进度日志、远端转交和实际产物检查。HTTP/MCP 让外部脚本或 AI 调用这些能力。

这种组合的意义是减少工具之间的手动搬运，并为后续媒体资料工作流提供任务状态和成品路径。它并不因此自动具有视频理解、转写、摘要或知识库检索能力。
