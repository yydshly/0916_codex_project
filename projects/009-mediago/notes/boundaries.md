# 能力边界与研究价值

研究提交：`f2aa40a8ce7cdd02fae7cf9b13b0860f29eb5088`。E 编号见[源码表](sources.md)。下文区分源码事实与待测影响，不将静态阅读写成运行结果。

## 1. 支持站点不等于下载成功

| 层次 | 含义 | 结论 |
| --- | --- | --- |
| 页面可识别 | MediaGo 对 URL 或页面资源有匹配规则 | 共享规则覆盖部分主流站点与媒体后缀 |
| 引擎可处理 | BBDown/yt-dlp 等支持目标 | 依赖工具及其版本；范围可能大于自动识别 |
| 当前内容可下载 | 网络、会话、签名和媒体数据均有效 | 必须实测，本次未验证 |

`InferDownloadType` 对未匹配网站默认返回 `direct`，不会把所有未知页面交给 yt-dlp。即使 yt-dlp 支持某网站，省略类型也可能路由为文件下载，需要明确选用适当类型并验证。证据：E01、E05。

HLS 读取与普通加密流处理也不能推出通用 DRM 解锁能力。本次没有建立 Widevine 等绕过的实现证据，未验证会员、付费和地域受限内容。

## 2. 源码中的具体限制

| 观察 | 源码事实 | 影响与验证程度 |
| --- | --- | --- |
| Docker 网页发现依赖执行端 | browser 路径检查 executor；已读实现由 Electron 连接 bridge | 不能认定 Docker 独立具备完整嗅探；扩展可以在用户浏览器发现后发任务。静态确认 |
| direct 参数映射不完整 | 默认 direct schema 没有 headers/proxy；buildArgs 按 schema 遍历 | 默认配置下不代表字段传给了 aria2c；防盗链直链需实测，自定义 schema 可改变行为 |
| 发现结果短期保存 | 默认保留 10 分钟，容量 20；私有头存内存 | 不能当永久素材库；过期或重启后可能需要重新发现 |
| 延迟启动有上下文边界 | 本地发现立即启动时才注入 runtimeHeaders；敏感头不进入记录 | 先创建后普通启动不能保证带回原 Cookie；影响待实测 |
| Docker 转交不同于本地发现 | 私有头发送到远端普通任务接口，普通创建保存 Headers | 不能全局承诺 Cookie 不落库。静态调用链确认，非完整安全审计 |
| 有文件不等于媒体完整 | 检查真实产物，但默认 HLS 关闭分片数量检查 | 时长、解码、音画同步、缺片仍需验证 |
| 内存队列与记录分开 | 活动状态、取消与调度保留在内存，数据库保存记录 | 不承诺宕机续传、分布式调度或恰好执行一次，未测恢复 |
| 控制台输出有版本耦合 | 正则识别进度/直播，依赖固定版本 | 升级须验证参数、输出解析及产物识别；上游测试未执行 |

证据：E05–E10、E15–E17、E23–E25。这些是使用和工程边界分析，不是已提交或已复现的 Bug 报告。

## 3. 文档与源码差异

README 展示稳定版 3.5.0，本次分析的是 2026-08-29 master 提交。MCP、媒体发现、小红书通道和 Docker 代理等源码能力，不能仅凭版本号断言全部发布安装包都包含。

- 官网 API 文档写 Docker 端口 9900，而快照 Docker entrypoint、Dockerfile 和 compose 使用 8899。地址应以实际启动配置为准。
- 官网示例使用 `waiting`，Core 当前为 `pending`；数据库另有旧 `watting` 到 `pending` 的迁移。接入方不应只按旧示例硬编码状态。
- 进度节流注释写 200ms，函数条件实际是 50ms。执行表达式比注释更能说明当前行为。

证据：E05、E09、E18、E22；在线对照：[官方 API 文档](https://downloader.caorushizi.cn/api.html)。差异尚未通过服务实调验证。

## 4. 对我们的用途

| 场景 | 可借助的能力 | 尚需补充 |
| --- | --- | --- |
| 保存自己或获授权的视频资料 | 发现、下载、转码集中操作 | 目标站点实测与内容管理 |
| 服务器/NAS 下载 | 浏览器发现、远端下载和存储 | 网络、目录、凭据路径验证 |
| AI 指令采集资料 | MCP/HTTP 创建和查询可追踪任务 | 转写、摘要、索引与检索 |
| 学习跨平台工具产品化 | 子进程适配、任务模型、SSE、SQLite | 实际构建和资源使用评估 |
| 接入自有工作流 | 复用服务接口与任务管理 | API 版本适配、产物取用、重试策略 |

若目标是媒体下载入口或服务器下载服务，参考价值较直接；若仅下载少量明确支持的链接，单独调用引擎可能已足够。这是架构与范围判断，没有效率对比实测。

## 5. 值得借鉴的设计

1. 发现与执行分开，先整理可选资源，再创建任务。
2. 对外部引擎统一适配参数、日志、取消与错误。
3. 保存实际产物路径及多个输出，减少按名称猜文件。
4. HTTP 与 MCP 共用业务服务，减少入口行为分叉。
5. 固定二进制版本和 SHA-256，并用输出契约测试辅助升级。

本次未移植代码。后续分发上游或外部二进制应核对各自许可材料，根 MIT 文件不能替代所有依赖许可证。证据：E17、E19、E23。

## 6. 后续验证方案（未执行）

优先用本地生成或明确获授权的样本，将站点变化和产品逻辑分开验证。

| 实验 | 目标 | 验收方法 |
| --- | --- | --- |
| 本地直链与请求头保护直链 | direct 参数和文件正确性 | 对比文件 SHA-256，记录鉴权响应 |
| 两档分辨率 HLS | 主列表检查、变体选择、合并 | 核对 URL、输出分辨率、时长及解码 |
| 无后缀 HLS 和伪 HLS 响应 | 桌面 Content-Type 候选检查 | 真清单被发现，假内容被排除 |
| 延迟加载页面 | 发现等待、超时和取消 | 记录部分结果，检查是否有过期回报 |
| 短直播手动停止 | 收尾与保留分片恢复 | 核对可播放性、时长和恢复日志 |
| 并发、重复提交及重启 | 队列和状态恢复 | 检查同一任务是否重复运行、记录和文件是否一致 |
| 本地与 Docker 发现转任务 | 凭据生命周期差异 | 用虚构会话标记检查返回、数据库、日志及临时文件 |
| MCP 全流程 | 发现→选择→下载→查询 | 工具结果与实际产物一致，执行端缺失错误可理解 |

以上是下一轮可执行研究方案，不是已通过测试。本轮完成标准是固定版本分析、证据整理与项目收录。
