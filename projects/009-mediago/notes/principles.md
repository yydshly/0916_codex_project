# 工作原理与技术本质

分析针对 `f2aa40a8ce7cdd02fae7cf9b13b0860f29eb5088`。E 编号对应[源码表](sources.md)，全部是静态阅读结论，没有运行端到端下载。

## 1. 技术本质与分层

用户通常给出“能播放视频的网页”，下载引擎需要的却可能是媒体清单、站点标识、文件地址及访问上下文。MediaGo 将前者转换为后者，再统一管理执行过程和结果。

| 层 | 负责什么 | 主要技术 |
| --- | --- | --- |
| 交互入口 | 浏览页面、选择资源、展示进度、接收工具调用 | React、Electron、Chrome/Edge 扩展、HTTP、MCP |
| 资源发现 | 区分页面与媒体资源，检查 HLS，关联请求头 | webRequest、站点适配器、Go 清单检查 |
| 任务控制 | 持久化、去重、并发、取消、记录产物与事件 | Go、Gin、GORM/SQLite、SSE、内存队列 |
| 下载与处理 | 站点解析、传输、分片合并、转码 | 外部下载器与 FFmpeg 子进程 |

工程价值集中在层间接口：有效输入如何传递，取消与失败如何收敛，最后到底生成了哪个文件。依据：E01–E13、E19。

## 2. 网页视频如何被发现

**请求级发现：** Electron 的 `SniffingHelper` 注册 `onSendHeaders` 与 `onHeadersReceived`，获取 URL、请求头及响应的 HLS Content-Type。共享规则匹配 URL pathname，避免仅因查询参数出现媒体后缀而误判。无 `.m3u8` 后缀但返回 HLS 类型的候选，还会接受内容检查。（E01、E02）

**页面级识别：** 对 B 站、YouTube、X、抖音/TikTok、小红书的相应页面模式，将页面地址交给 BBDown 或 yt-dlp。这里复用专门引擎对网站的理解，不要求浏览器先提取到最终文件地址。共享浏览器包中还有站点适配器。（E01、E05、E20）

最终 Chrome/Edge 扩展在 `packages/mediago-extension`；`packages/browser-extension` 是共享浏览器/站点适配包，不能只根据目录名判断用途。扩展使用 `chrome.webRequest` 并调用 Core。桌面与扩展共享规则，但事件处理不完全相同：此次在桌面明确查到的 Content-Type 候选机制，不直接推广为扩展的同等能力。（E02、E03、E20）

### 为什么只复制 URL 可能失败

媒体请求可能依赖 Cookie、Referer、User-Agent 或签名参数。代码会保留请求上下文并在部分引擎通道中使用；yt-dlp 的 Cookie 被写入临时 Netscape Cookie 文件，结束后清理。小红书 URL 规范化仍保留查询参数。（E05、E10）

所以浏览器当前能播放，不代表另一个进程或服务器只凭同一 URL 就能下载。上下文、网络出口或签名有效期发生变化，都可能影响结果；具体站点须实测。

## 3. HLS：清单检查与实际下载分开

HLS 播放列表是文本：主列表描述不同码率、分辨率的变体；媒体列表描述分片；直播列表可持续更新。分片可以是 MPEG-TS 或 fragmented MP4 等格式。保存一个 m3u8 文件并不等于保存完整视频。[协议依据：RFC 8216 第 2–4、6 节](https://www.rfc-editor.org/rfc/rfc8216.html)。

MediaGo 将流程分为两部分：

1. **M3U8Inspector** 获取清单并检查 `#EXTM3U`，解析列表类型、变体 URL、分辨率、带宽、编码信息。这主要给界面和调用方提供选择依据。（E04）
2. **下载引擎** 接收清单 URL，下载数据并合并。默认 `m3u8` 通道使用 N_m3u8DL-RE，参数包含自动选择和 FFmpeg 路径。`mediago` 另指向一个外部二进制，本次没有进一步审计该独立引擎算法。（E05、E06）

检查器设置 5 秒请求超时、2 MiB 清单上限、最多 4 个批处理 worker，以及 5 分钟/500 条缓存。缓存键包含 URL 和请求头的 SHA-256。显示清晰度来自清单声明，不是对完整视频解码后的测量。（E04）

发现转下载接口只接受源 URL 或该资源已检查出的变体 URL，限制任意地址混用私有请求上下文。（E15）

## 4. 多下载引擎的统一适配

`BinaryNames` 定义六种类型与五个执行入口：

| 类型 | 二进制 | 用途 |
| --- | --- | --- |
| `m3u8` | `N_m3u8DL-RE` | HLS 主下载通道 |
| `bilibili` | `BBDown` | B 站专用解析与下载 |
| `direct` | `aria2c` | 文件下载；当前分发源为 aria2-next |
| `youtube` | `yt-dlp` | 多站点解析通道，名称不代表仅支持 YouTube |
| `xiaohongshu` | `yt-dlp` | 小红书独立类型与特定处理 |
| `mediago` | `mediago` | 另一外部引擎通道 |

`Schema` 把 URL、文件名、目录、请求头等字段映射为具体命令行参数，并为每个引擎配置开始、进度、速度、错误与直播的输出匹配规则。无外部 schema 文件时使用内置默认值。（E05、E06）

这是一种可配置适配层，但新引擎仍可能需要改类型、依赖准备、结果识别及交互；不能概括为改一份 JSON 就支持任何工具。

## 5. 任务、并发与持久化

`DownloadTaskService` 检查重复 URL、准备合法且可用的文件名并建立记录。SQLite 保存任务、收藏、转换记录和产物；运行中状态和队列位于内存。`TaskQueue` 限制同时执行数量，对同一任务 ID 重复入队做处理，通过取消上下文停止工作。（E07–E09）

两个并发维度需区分：队列控制同时运行几个视频任务；direct 默认的 `-x 16 -s 16` 是引擎内的连接/分割设置，不能当作实际加速倍数。（E06、E08）

状态为 `pending / downloading / success / failed / stopped`。SSE 推送相关事件，查询接口提供可读取的状态。数据库保存记录不自动等于宕机恢复完整队列、跨机器调度或恰好执行一次。（E05、E08、E09、E21）

## 6. 子进程输出如何变成进度与结果

各工具输出格式、字符编码和进度条更新方式不同。运行时默认采用 PTY Runner，也提供普通管道 Runner；Windows 与 Unix 有独立平台实现。控制台文本由解析器统一为状态，再对进度更新节流。（E10、E22）

这让成熟 CLI 能进入统一界面，也产生了版本耦合：引擎升级或输出语言变化可能使进度、速度和直播识别失效。上游固定二进制版本并提供输出契约测试。本次阅读了相关测试，未执行。（E06、E17、E23）

**成功判断包含产物检查。** 下载前后采集输出文件状态，根据名称、变化和引擎报告路径确认产物。yt-dlp 通过专用输出标记返回最终路径。若没有符合条件的媒体文件，会返回输出缺失错误；HLS 对合并产物另有检查。成功回调保存真实输出路径，然后广播事件。（E10、E21）

这能降低“显示成功但没有文件”的概率，却不证明视频完整、全部分片齐全、画面可解码或音画同步。默认 HLS 参数显式使用 `--check-segments-count false`，不能把成功状态描述成完整分片验收。（E06、E10）

直播有特殊收尾：识别为直播后先尝试有时间上限的温和停止，再检查文件，必要时恢复保留分片。因此停止直播也可能进入成功保存状态；异常后恢复的文件也不等于整场直播完整录制。（E10、E21）

## 7. 转换格式的本质

转换服务调用 FFmpeg。mp4/mkv 走 H.264 与 AAC，webm 走 VP9 与 Opus，音频输出支持 mp3/aac/flac/wav。质量配置映射到 CRF 或音频码率，进度根据媒体时长与处理时间估算。（E11）

这是重新编码或音频输出；质量选项不能恢复原视频没有的细节。具体编码器是否可用、质量和速度如何，还依赖打包的 FFmpeg 与实际媒体样本。

## 8. AI、HTTP 与 MCP

仓库 Skill 是供 AI 助手使用的 HTTP 调用说明，要求已有运行中的 MediaGo。它不在下载器里提供视频理解模型。（E14）

当前 Core 还实现 `/mcp` Streamable HTTP 服务，需要启用并配置 token。工具共 9 个：`health_check`、`discover_media`、`get_media_discovery`、`cancel_media_discovery`、`download_discovered_media`、`create_download`、`get_download`、`list_downloads`、`stop_download`。（E13）

发现支持 auto/browser/inspect。auto 对 pathname 以 `.m3u8` 结尾的 URL 选择清单检查，其余走浏览器；执行端不可用会报错。这是明确规则，不是 AI 自行推理解析算法。（E12）

AI 可以理解需求、选择资源、调用工具和查询结果。站点解析、传输和合并仍是原有下载链。转写、摘要、知识库检索属于可外接流程，没有被本次所读核心实现证明为内置能力。

## 9. 桌面、Core 与 Docker 协作

Go Core 提供 API、任务服务和嵌入式 Web/播放器资源。Electron 增加窗口、浏览器和会话能力。Core 通过 bridge 分发发现任务，Electron 执行网页并回报资源；执行代次和取消信号用于阻止过期回报。（E12、E18、E24）

Agent 发现默认使用临时会话，仅 `useSessionCookies=true` 时使用桌面默认会话。公开发现结构不含 Headers，私有头留在 Core 内部。本地发现转下载仅把敏感头注入执行队列，持久化安全子集。（E15、E24、E25）

`/api/docker/...` 将任务代理给配置的远端 MediaGo，实现本地发现、远端下载。它并不等于容器集群的分布式调度。（E16）

**路径差异：** Docker 发现转交把私有头放进远端普通 `/api/downloads` 请求，普通创建又直接保存 Headers。不能将本地发现的“敏感头不持久化”推广到 Docker 转交或全部手动任务。这是静态调用链结论，未连接远端验证。（E07、E15、E16）

## 10. 可复用的技术思路

主要价值是工具产品化：外部引擎提供站点和传输能力，MediaGo 提供统一入口、上下文传递、任务状态和产物管理。最值得借鉴的是发现与执行分开、统一任务模型、记录真实产物，以及一个业务服务对接多个入口。

它可以成为媒体资料流程的前段。资料库仍需要额外实现转写、标签、检索和生命周期管理；可靠性评价仍需要真实样本与故障实验。
