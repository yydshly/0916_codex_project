# 可靠性与场景判断

这些是基于固定研究版本和本轮实验形成的工程判断，不是 Wren 官方准确率承诺，也不是完整业务系统的验收结果。技术来源见 [源码研究](research.md)，实际结果见 [引擎记录](engine-verification.json)。

## 我们对落地思路的理解

Wren 将模型理解与业务工具结合：资料定义业务，模型结合上下文生成操作，Agent 调用工具，引擎展开定义，计算层返回真实数字，再由应用解释和展示。仅增加提示词约束不足以覆盖这条链路。

“规则匹配”需要区分：RAG 找相关说明；大模型理解并尝试在 SQL 中应用；引擎执行结构化定义。检索到规则不代表执行了规则，SQL 合法也不代表选对了业务口径。

### 准备与运行

准备期：业务表与数据质量 → MDL 定义与编译；文字规则与正确 SQL → 可选索引；模型服务与数据库连接 → Agent 工具。

运行期：问题理解 → 检索 → 模型生成 → Agent 调用 → Wren 展开和校验 → 数据库计算 → 模型解释 / 前端展示 → 确认后积累案例。步骤可重复或按需省略；信息不足应追问，错误应返回修正。

## 哪些场景适合

| 场景 | 判断 | 前提 / 输出 | 复核重点 |
| --- | --- | --- | --- |
| 销售经营问数 | 优先试点 | 固定净收入、订单等口径；地区和客户分析 | 对账、跨月退款、内部订单、重复计数 |
| 运营与订阅报表 | 定义清楚后适合 | 活跃 / 留存 / 续费 / MRR 定义；常规指标报表 | 用户去重、分母、统计窗口、月化方式 |
| 库存与履约 | 适合结构化分析 | 可用库存、在途和周转定义；缺货与时长分析 | 时点库存、迟到记录、重复同步 |
| 分析师探索和复杂指标 | 辅助使用 | 数据粒度、归因与时间范围明确；候选 SQL 和探索结果 | 分析师审查 JOIN、分母、样本和业务解释 |
| 付款、审批、自动下单 | 需要独立业务流程 | Wren 可提供查询证据，交易 API 等负责执行 | 授权、审批、幂等、状态和金额校验 |
| 预测、因果与经营建议 | 查询只提供证据 | 需要额外预测 / 因果方法及验证数据 | 留出数据评估；结论与证据是否匹配 |

## 分层可靠性

1. 数据与 MDL：错误字段映射、退款日期归属、币种或粒度会让可执行查询产生错误业务答案。由业务负责人确认，并对照现有报表。
2. 检索：可能遗漏关键规则、召回过时文档或遇到冲突定义。检查相关性、版本、适用范围与召回证据。
3. 模型生成：可能选错日期、条件、分组或 JOIN。使用真实问题与标准答案核对输出，不只评价 SQL 语法。
4. 引擎与数据库：可以发现部分字段和语法错误，不能自动判断用户的真实业务意图。执行测试需要结合业务验收。
5. 模型解释：只能陈述返回数据支持的结论；单期收入不足以得出增长，更不足以确定原因。

具体例子：“按订单月扣退款”和“按退款实际发生月扣退款”都可能产生合法 SQL；跨月退款时答案不同。系统需要清晰口径和标准结果，而不是只增加一次 SQL 校验。

## 已验证与未验证

已验证合成数据的 36 组预设 WASM 查询、计算字段、显式关联、筛选聚合、排序、错误字段与前端交互。结果与独立计算一致。

未验证自然语言理解、RAG、模型自动生成 / 修正 / 解释、生产数据库、业务权限与性能。36 组固定查询通过，不代表端到端问数准确率为 100%。

建议首个试点：固定指标 + 少量核心表 + 只读查询 + 可核对标准答案。先覆盖日期、退款、JOIN 粒度、歧义追问和空结果，重要结果保留人工复核，再扩大范围。
